# Beautiful Mermaid Rust

An independent, native Rust diagram library ported from Beautiful Mermaid
1.1.3. It parses Mermaid, estimates text dimensions, lays out graphs using native
ELK and diagram-specific Rust geometry, and emits standalone SVG. It requires no
JavaScript runtime, browser, Node, Java, remote font service, or application
framework at runtime.

This preview implements all six Beautiful Mermaid families: flowchart, state,
sequence, class, entity relationship (ER), and XY chart. It is not a complete
Mermaid language implementation. The parent application's Markdown reader and
HTML reports now prefer this library, with the previous native renderer retained
as a fallback for other syntax. The crate remains independently buildable, with
its own manifest, lockfile, tests, license, and upstream attribution.

## Library use

```rust
use beautiful_mermaid_rs::{render, theme, RenderOptions};

let options = RenderOptions {
    colors: theme::theme("zinc-dark").unwrap(),
    ..RenderOptions::default()
};
let svg = render("flowchart LR\nA[Start] --> B[Done]", &options)?;
Ok::<(), String>(())
```

`render` dispatches all six families and returns an SVG string. `layout` returns
a typed `PositionedGraph` for flowcharts and states. Sequence, class, ER, and XY
modules expose their own typed parse/layout APIs. `parser::parse` and
`layout::build_elk_graph` expose the intermediate representations for diagnostics and reference tests. The top-level
source APIs decode XML entities once, validate options, and return errors for
unsupported input. Rendering is synchronous: call it from a worker rather than
an application's frame/render callback.

From this directory:

```sh
cargo run --release -- fixtures/gates.mmd output/gates
cargo run --release -- fixtures/nested.mmd output/nested
cargo test --release
cargo clippy --release --all-targets -- -D warnings
```

The CLI writes light/dark SVGs and, for flowcharts and states, positioned
geometry. Output and build artifacts are ignored. Use this directory as a path dependency today; no
crates.io name has been reserved or published.

## Ported behavior

- State aliases, descriptions, start/end pseudostates, labeled transitions,
  composite states, and direction settings.
- Sequence participants/actors, messages, self messages, inline activations,
  notes, and control blocks with dividers.
- Class compartments, annotations, generic labels, member visibility and
  modifiers, relationship markers, labels, and multiplicities.
- ER entity attributes, PK/FK/UK badges, comments, identifying/non-identifying
  relationships, and crow's-foot cardinalities.
- Vertical/horizontal XY charts with bar and line series, categorical or numeric
  x axes, numeric y axes, titles, grid lines, and OKLCH-derived series colors.
- Flowchart directions, node shapes, chained and parallel edges, labels,
  arrowheads, dotted/thick connectors, classes and explicit styling.
- Variable-width text estimates: Latin character buckets, CJK/emoji, combining
  marks, font-weight ratios, multiline dimensions and inline formatting.
- Upstream node sizing, graph spacing, ELK options, nested groups, top-level
  subgraph direction overrides, hierarchical edge routing, layer alignment and
  edge bundling.
- Shape geometry, group header bands, label backgrounds, font sizes/weights,
  marker dimensions, all 15 upstream themes and optional color overrides.
- Cross-boundary edges use the ELK container's coordinate origin. This fixes
  disconnected nested paths observed in the pinned upstream output.

This independent crate does not depend on `mermaid-rs-renderer`; the parent app
retains it only for fallback rendering. All library implementation and runtime dependencies are native Rust. Optional JavaScript
files under `tools/` exist only to refresh upstream test references.

## Verification and limits

`fixtures/reference` contains inputs and outputs generated by **Beautiful Mermaid
1.1.3 / ELK.js 0.11.1**, not generated by this Rust implementation. UPSTREAM.json
records package integrity, source checksums, and the native ELK version.

Tests compare parser/layout input and positioned geometry against the reference,
plus check nested membership, child containment, finite on-canvas paths, and
attached edge endpoints. Nested native layout differs from ELK.js placement, so
it is tested for correctness rather than falsely asserted pixel-identical.

Raster comparisons for the supplied Chinese graph in light and dark, a cycle,
a shape/style fixture, class, ER, and XY fixtures matched the pinned reference exactly after resolving
CSS colors and using the same local font stack. These are fixture-specific
results, not guarantees across fonts, platforms, or arbitrary diagrams. See
VALIDATION.md for the concrete checks and known differences.

Current boundaries:

- Supported headers are `graph`/`flowchart`, `stateDiagram[-v2]`,
  `sequenceDiagram`, `classDiagram`, `erDiagram`, and `xychart[-beta]`.
  Unsupported directives fail rather than silently disappearing.
- State notes, fork/join/concurrency directives, class namespaces, sequence
  autonumber and standalone activate/deactivate directives, and sequence cross
  arrowheads are not implemented. Inline sequence activation markers work.
- Class layout uses the upstream downward direction; ER uses rightward layout.
  XY supports numeric y axes only, requires equal-length series, and rejects
  nonfinite values, invalid ranges, and data outside an explicit y range.
- Direction overrides are supported on top-level subgraphs. Overrides inside
  nested subgraphs fail explicitly pending further upstream/native validation.
- Library input is limited to 64 KiB. Graphs have 100-node/200-edge guards and
  16 nested group levels; sequence has participant/message/note
  guards; class/ER have entity/member/relationship guards; XY allows at most 32
  series with 1,000 values each. These are resource guards, not a complete sandbox
  or guaranteed layout time budget. The app imposes 16 KiB and 256-line limits.
- Text measurement intentionally follows upstream estimates rather than shaping
  actual installed fonts. Emoji classification follows Rust regex Unicode data.
- Colors support hex RGB and a small named-color set. CSS variables, arbitrary
  CSS expressions and external color references are rejected. Theme colors are
  materialized as RGB for native SVG decoders; fonts use local fallbacks.
- Some upstream permissive parsing is intentionally stricter here: malformed
  trailing syntax and unclosed groups return errors rather than partial graphs.
- There is no HTML DOM interaction, external font fetching, SVG animation, or
  Shiki integration. This is a static SVG library.

## Reproduce upstream comparisons

Normal Rust tests do not need Node. To refresh the oracle, install the exact
Beautiful Mermaid and ELK.js versions in a separate temporary directory, then
run this development-only script with Node 24+:

```sh
node tools/generate_reference.mjs /absolute/path/to/node_modules/beautiful-mermaid fixtures
```

The script imports an external pinned upstream package and never uses the Rust
renderer to produce reference fixtures. It checks both the Beautiful Mermaid and ELK.js versions. Raster comparison additionally needs Python,
`rsvg-convert`, and ImageMagick on the development machine:

```sh
python3 tools/compare_svg.py fixtures/reference/gates.zinc-dark.svg output/gates/dark.svg output/comparison/gates-dark
```

## Open-source preparation

Our port retains Beautiful Mermaid's MIT notice. Native ELK has separate license
terms; see THIRD_PARTY_NOTICES.md and the license files. `publish = false` remains
until package naming, API review, dependency notices, cross-platform CI and
release scope are finalized. No repository, package, or app release is published
by this work.

Nested sequence control blocks return an explicit error in this preview because overlapping header geometry is not yet supported. The parent app can use its compatibility renderer for these inputs.
