# Task Manager interaction design

## Direction

Keep the existing native workspace layout, system fonts and warm neutral palette. Light mode serves daytime reading and dark mode serves dim environments; both must show control boundaries at rest. Default pages serve non-developer research workflows, with technical configuration and diagnostics on demand. Preserve the existing palette, button discoverability and all execution capabilities.

## Components

- Primary: solid deep warm fill (solid light warm fill in dark mode) for create, generate, save and run. Emphasize one advancing action per local action group.
- Secondary: always-visible neutral surface and full border for frequent supporting actions such as settings, edit, copy, close or back. Never make these ghost buttons by default. `controls::quiet_button` is the standard; `controls::row_button` is only for compound surfaces that already provide their own boundary: sidebar/tree rows, board cards, popup menu rows and segmented controls. Task tabs keep their own shared-border rule below.
- Action hierarchy: reserve the primary fill for the one advancing action in a local group. Use secondary controls for frequent supporting actions, direct Lucide icon controls for compact well-understood actions, and a More (…) menu for suitable low-frequency actions. Do not render every action as an equally prominent button, and do not flatten everything to ghost styling either. Each icon/More trigger keeps a full hit area, tooltip and meaningful accessibility label, and its destination or state must stay unambiguous.
- Selection: bordered selection control; the selected state uses an accent surface/text and a clear visual change, and also sets the toggled semantic state. `controls::select_button` owns this appearance; selection never borrows the primary fill. Selection stays distinct from the one advancing action in the group.
- Link: underlined accent text for navigation, sources and opening files; body-text URLs follow the same rule. Settings actions remain buttons.
- Icon: fixed square hit area, full boundary, tooltip and accessibility_label. `controls::tool_icon` supplies that boundary; never leave a bare × or +. The same control may host a More menu for low-frequency actions, but must not hide the page's main action or an important disabled reason.
- Task tab: the title and close icon share one background and border, with no separate button border inside. The close icon is always visible and keeps its own hit area, hover and focus feedback. Long titles ellipsize to the available width, reveal the full name on hover, and never compress the close area.
- Danger: red outline and tint via `controls::danger_button` for stopping an active run, cancelling an active period or removing material. Ordinary Close or Cancel uses the secondary control, not danger color.
- Disabled: keep the shape, weaken fill and text, and explain the business reason near the button; never trigger the action.
- Focus: keep the component library's focus drawing and Tab/Enter/Space semantics; hover alone is insufficient.

## Geometry and typography

Action buttons are about 32 px tall with 6 px radius and 14 px system font; Undo in the bottom status bar uses a compact 24 px button. Toolbars stay on one line and truncate long titles instead of compressing buttons. Horizontally scrollable boards keep their current column widths. Form/detail action rows may wrap. Sidebar content scrolls and the theme switch stays fixed at the bottom instead of being pushed out as projects grow.

## Workspace identity and status bar

- Workspace identity is fixed at the bottom of the sidebar on the same row as the theme switch and replaces the standalone Settings nav item: name, local-storage icon and a dropdown menu. The menu offers Reveal data folder, Copy data folder path and Settings…; the storage location, the backup entry point and the Settings page all start here. The row shows the selected state while Settings is open.
- The left side of the status bar reports only persistence state and the latest action feedback. Saved uses a neutral check; writing uses the accent dot with "Saving changes…"; a failed save uses the danger tone with the reason and a Retry save action; unavailable storage explains that changes are only in memory.
- The right side of the status bar holds only real commands: Undo, Search, New research. Shortcuts are stated in tooltips (⌘K / ⌘N) instead of rendering shortcuts as non-clickable body text. A disabled Undo explains why in its tooltip: nothing to undo, submitted work must finish first, or automation changes are protected from whole-store rollback.

## Boundaries

Non-interactive chips, task statuses and field labels keep low contrast and no button border. Clickable lists/cards need hover feedback and a visible open arrow or action; do not give body copy a button shape. Sidebar chevrons mean disclosure only: rows that expand on click (projects, topics, goals) keep a chevron, while plain navigation rows show only their count. Shortcut navigation keeps the sidebar structure. In All research and Archive, the goal completion count is a compact navigation control with a fixed right chevron: it opens that goal’s Steps tab. It does not expand inline children. Back restores the originating collection’s filter and scroll position.

Automation history rows keep one neutral surface and express state through semantic status text and accents rather than a large row fill. Trigger source shows a compact Manual/Scheduled text label beside its icon, with skipped-period detail in the tooltip. Long automation names and step titles ellipsize but keep the complete value in the tooltip and accessibility label. Recently opened menu labels wrap to the menu width and keep the complete value in the tooltip instead of collapsing to an unexplained short prefix.

Readable text must be drag-selectable and copyable with ⌘C: body copy, titles, descriptions, reports, setting values, automation summaries and history all render through `views::selectable` (reports use TextView's built-in selection). Button text, navigation items and compact labels manually ellipsized on canvas do not participate in selection, preserving click semantics and truncation accuracy.

## Scrolling acceptance

Actual scrolling smoothness on the isolated native application is mandatory and is defined by the authoritative [scrolling acceptance contract](doc/review-2026-11-08/TASKS.md#mandatory-scrolling-acceptance). Static screenshots, averages or synthetic slices do not satisfy it. Under the first-round acceptance update, occasional isolated hitches may be documented and deferred; repeated or sustained stalls and incorrect scrolling remain failures.

## Source of truth

`appearance.rs` owns theme and component colors. `controls.rs` owns button/link factories. Pages choose action semantics and bind behavior only; do not reintroduce a global ghost default. Strike the hierarchy from one advancing primary action per local group down to secondary, icon and More actions; verify it in both themes. Native screenshots and interaction acceptance cover 1440×920, 1000×680 and both light and dark themes.

## Model settings

The global model entry sits at the bottom of the sidebar. The global page combines the default model, an independently searchable local model list, save actions and the current override list. An empty stage input inherits the global setting, and the field shows the effective model and its source; clearing an override takes effect only after saving. "Use this model for all stages" on the global page is an explicit option; saving never starts a task or changes history. Project planning windows and task details show the same effective-model rules.

When every stage inherits, the checkbox stays checked according to the actual configuration and acts as a read-only state; changing one stage override allows unifying again. Save feedback sits in a dedicated area at the top of the main content and never floats over edit buttons. Success and failure combine an icon, title and explanation; On the live v4 path, Saving remains visible while the ordered worker has an outstanding write; Saved appears only after the matching durable acknowledgement. A failed save retains its retryable intent and never claims success. Legacy/offline synchronous paths report their actual save result. Final runtime and performance acceptance remains tracked in the review documents. Feedback can be dismissed, and changing pages or abandoning a form clears the old message.

Inline notices use semantic tones: success green, warning orange, error red, neutral information gray. Each notice is a rounded box with a tinted surface: the background blends the tone with the panel color, and the border and text use the same tone; avoid weak "white fill + colored outline" styling. All colors come from `Palette`; dark mode automatically uses the dark panel with the same semantic color, and hardcoded light backgrounds are forbidden.

## Sidebar order

The sidebar presents two domains in this order: **Automations** (All automations, Automation results) above **Research** (All research, projects, Paused projects, Research results, Archive). Archive belongs to the Research group rather than sitting as an unlabelled bottom row, so a long sidebar always makes its scope clear.

## Automations

The maintained current/target route and action contract is [doc/ROUTE_ACTION_MATRIX.md](doc/ROUTE_ACTION_MATRIX.md); this section records the visual and interaction design.

- The sidebar separates **Research** and **Automations**. Research contains **All research** (all non-automation root tasks/goals), the project list, **Paused projects**, **Research results** and **Archive** for archived research only. Automations is a separate section containing **All automations** (the automation list) and **Automation results** (all automation period results) directly, not under Workspace alongside All, and with no expandable second-level parent. Automation results are fully separate from Research results; the latter contains only project/topic/goal research results. Automation periods use a separate concurrency pool (default 2, counting only running periods) and a separate queue; they consume no Research slots and never enter the Research Topic FIFO. Queue and slot explanations appear only on the Automations page and in period details. Both section titles are static labels; child items are directly visible and own their navigation. List rows use a compact two-line layout: the first line has the name plus type, status and unread labels; the second is a single-line summary of schedule, next trigger and the latest result with its activity time. Long names ellipsize on one line and never intrude into the right label area. The all-results list gives each automation a session-level name colour; every row shares one neutral surface and hover, and periods from the same automation share the name colour. The palette is not persisted and only aids grouping in the current session.
- Creation starts by choosing a shape (Quick task / Research automation), then entering one instruction or one-sentence request; choosing a project is no longer required. Both shapes use the same three steps: task → schedule/time zone/three previews → review. Quick's final step is authorization only because its single answer step is derived locally; Research's final step reviews the planner-generated goals before enabling. A fresh form starts from explicit defaults — Daily at 10:00 in the system time zone, Monday–Friday, LatestOnly, minute interval unit and default limits — and switching shape discards any plan approved for the previous shape. Going Back within the same draft keeps its entered values. A fixed bottom action bar shows Back, Save draft and Continue/Enable automation; saving a draft and enabling are two different visual levels. Leaving the creation page while planning keeps a **Planning…** label on the saved draft and a planning notice with a Review planning action on its detail page.
- The detail header gives status, type, version and owning project in one metadata line below the schedule instead of faking tabs with a chip row. Do not add a second back button: use the top breadcrumb Back, which shows Automations / current automation and returns to the Automations list. All automations and Automation results belong to the separate automation area and do not show Research's All research breadcrumb or a return-to-All-research button. The page prioritizes execution and results: the action row (Pause/Resume schedule, Run manually, Stop this run, Settings; Copy and Archive are not exposed yet) follows the header; history is a compact, expanded row list with one neutral surface per period and no per-row card border, sorted by the recorded latest-activity timestamp descending. Each period's activity key is its explicit retry request first, otherwise actual start, manual request, scheduled trigger or frozen reference time, with activity kind and ID breaking equal timestamps; a retry can therefore remain below another period after a backward clock change. Each row is already expanded to label the timestamp it uses (Retried, Started, Requested, Scheduled or Reference) plus status, trigger source and Open entry; unread still uses a dot, and rows do not expand further in place. In the all-results list, type and automation name occupy the first line, while timestamp, trigger and status share a wrapping metadata line. The quiet Open icon stays in a separate fixed-width action area, so long names or compact windows cannot push it outside the viewport. Definition history uses the same metadata and action alignment without repeating the automation name. Low-frequency destructive actions such as Cancel period live inside the result dialog details, not in each history row. Inline explanations for queued periods reference only the automation concurrency pool (running / limit), not Research concurrency or queues. Clicking a row opens that period's result in a dialog. Report, sources, a full-title step list with **Continue period** / **Retry period** above it for unfinished work (a failed, cancelled or interrupted period reopens in place with its original approved version and only unfinished steps rerun), and technical details all live in that dialog, technical details are collapsed, and a single run's logs scroll within a height limit. Definition, expected result, next three triggers, run boundaries (catch-up rule and per-run limits) and the approval snapshot live in the Settings dialog opened from the action row; Edit and Replan sit at the bottom of that dialog next to the settings they change, while the page itself keeps only execution actions. Dialogs use a modal scrim, focus trapping and Escape to close; long content scrolls inside the dialog. Quick periods use the short-answer contract: direct value or conclusion, as-of time, 2–5 sources and at most one or two material caveats; no appendix, methodology, evidence-requirement table, scenario analysis or next steps. Research periods keep the full report contract. Quick period time context shows only planned/actual start, time zone and reference time; the data window appears only when resolved. Pause and Run manually appear in the same position in every state: grayed out for drafts, with the unlock condition explained below the action row; only drafts cannot run before approval. Scheduled tasks and manual research share one execution path (same agent, working directory and output contract); do not maintain a second agent configuration and do not block enabling by build or by automation. Application-level run preconditions (runs only while the app is open and the computer is awake) sit at the end of the page, not mixed with per-automation information. While paused, Next runs shows a Paused marker and explains that resuming re-schedules, with no catch-up during the pause. Overview body text uses body size and primary color; explanatory text (Quick task description, run limits, disabled-time-zone explanation) uses smaller, muted text, and the two do not share a visual level. The next trigger shows local time only; the time zone already appears in the schedule summary, so do not repeat the abbreviation. Research creates one topic per period; the period topic name appears in the result dialog.
- History starts with 20 rows and **Load more**. The live v4 path requests indexed history pages asynchronously; legacy/offline paths may retain an in-memory presentation limit. Database/read-cost acceptance remains tracked under T14/T15. Unread uses a dot; skipped, failed, running and enabled are separate dimensions, not one status covering all.
- Step execution runs in phase order within each Goal — every collection step, then analysis, then the final report — and each step also waits for its declared prerequisites. A later phase never starts while that Goal's earlier phase is unfinished, even when the reviewed graph would allow it. Goals run in their approved order, so an earlier Goal finishes before the next Goal starts. Only the step whose own attempt failed is shown as Blocked; downstream steps stay Waiting, so the evidence → analysis → report order remains legible. Period and progress rows visibly state the same eligibility phrase, such as Waiting for collection or Queued for automation slot; the reason stays available on the task surface. Automation steps never use Research topic-queue guidance, and definition state remains separate from an active period.
- On storage failure, invalid forms or missing model/project/permission, use a dedicated error area with a reason and never show success. Log cleanup must preview first and state that results/sources are retained.
- Automation-internal Tasks/Topics/Runs are hidden from the normal board, sidebar tree and Research results by default; history results can explicitly open steps, and the breadcrumb returns to that period.
- Inside an automation period, Previous/Next follows only that period's ordered steps: goals in approved order, then workflow order within each goal. Boundaries disable instead of wrapping into another period or automation; a separate Overview action opens the period dialog. Ordinary research task navigation keeps its documented wrapping project-tree order.

## Progressive disclosure

- Daily navigation uses Research results; Settings → Agent & models shows the models used for planning, collection, analysis and reporting.
- Result surfaces use one typed presentation. The entry names **Final report**, **Partial period reports**, **Intermediate evidence**, **Live progress**, **Planning attempt**, **Task result** or **No report**. Evidence quality is a separate fact (**Complete**, **Evidence gaps**, **Needs input**, **Unverified legacy**, **Report rejected**, **Not validated**, **Incomplete**), and freshness labels can coexist (**Stale input**, **Regenerating**, **Original approved version**, **Historical result**, **Legacy result**). Streaming text is never styled as a validated final answer, and a failed period can still expose its finished step results.
- The execution page prioritizes task title, status, progress and report. Run history is a compact list; long titles use two lines and reveal the full name on hover. In-progress research protocols never render as reports.
- Technical details keep model, directory, session, time, exit status, Live logs and Saved output. A selected active task shows only one stop button, and batch controls stay visible outside the history list.
- The task page keeps start/view result, status, priority, project and due date by default. More details collapses low-frequency properties and execution settings; missing model or working directory shows a direct fix entry.
- The research page shows goal input and existing research by default; the **Research settings…** label opens the configuration page and input is preserved. Complete Back restoration remains a T10 acceptance item; do not promise it here as already delivered. Direct settings links must open the configuration page.
- Completed research steps use View result as the primary action; rerun is secondary. The goal result entry points to a valid research step and never treats planning JSON as a final report.

## Icon source and implementation

All interface icons use [Lucide](https://lucide.dev/icons/) via the pinned gpui-kit assets. Follow [Icon Guidelines](doc/ICON_GUIDELINES.md) for semantic choices, embedding, accessibility, exported reports, and verification. Replanned topics use NotebookPen with an explicit Replanned tooltip.
